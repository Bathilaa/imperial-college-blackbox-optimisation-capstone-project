Week 8 results: Function 1 up to 1.98 from 1.18, Function 6 and Function 7 also improved.
Function 4 returned -8.85, its worst reading yet.

How I prompted

Structured, not zero-shot. Each week I paste in a state summary: the current readings for
each function, what the leave-one-out check said last round, and what I tried last time.
Then I ask for the reasoning before any code. Early on I used short open questions like
"what should I query next" and got answers that were fluent, confident and impossible to
check. Giving it the numbers and asking it to argue for a choice produced answers I could
test against the data. I also ask for the plan in plain language first. If it cannot
explain the idea simply, I usually do not understand it well enough to defend it here.

Decoding settings

I worked in chat interfaces, so temperature, top-p and top-k were not exposed and I did
not set them. Driving this through an API I would keep temperature low for anything that
produces a number I am about to submit, because I want the same answer twice from the same
data. I would raise it only when asking for alternative strategies, where I want a spread
of ideas rather than the single likeliest one. That is the same trade-off as my
acquisition function. Expected Improvement is the low temperature choice and Upper
Confidence Bound is the high one, and this week six functions sat on EI and one on UCB.

Token limits

I have not hit truncation. I checked by asking for the same round of queries twice in
separate conversations and comparing the numbers, and by keeping the readings in .npy
files rather than in the prompt. With eighteen readings on the smallest
function and forty-eight on the largest, the summary is still short. Run to thirteen rounds
it would be close to 300 readings, which is the point where I would pass file paths instead
of pasting data.

What went wrong

Round 7. I had a good point on Function 1, probed 0.03 to one side, found it cost almost
nothing, and accepted the reasoning that the ridge was therefore symmetric so I could step
0.12 the other way. Nothing in my data said it was symmetric. The value fell from 1.18 to
2.2e-13. The limitation was not an invented fact, it was a plausible assumption I never
made it check against an actual reading. Round 8 only queried between points I already
held and returned 1.98, the best of the run.

Stopping it making things up

Three things, in order of how much they helped. I made everything a script that reruns
from the saved data, so a claim has to survive being executed. The notebook in my repo
regenerates my round 8 queries and compares them against the file I actually submitted,
and prints whether they match. I put the same state summary to two different models and
look at where they disagree, which is where I go and check. And I stopped one of them when
it referred to a function's true optimum, which is not something either of us can know
from eighteen readings. That was the most useful catch of the run and it came from me
reading carefully, not from any setting.

Scaling this up

The prompt is the part that would break first. More functions or more readings and I would
stop pasting numbers entirely, pass file paths, and move the repeated weekly reasoning
into code so the model only handles the part that actually changes each round. I would
also want the checks automated rather than me noticing things, because I will not catch
the true optimum claim every time.

Working without knowing the answer

Every one of these choices is the same problem as the capstone itself. One query per
function per week is the entire budget, so a wrong step costs a week. Low temperature and
tight grounding are the exploitation setting, loose prompting is exploration, and Round 7
is what exploration costs when nothing constrains it. The useful habit was not trusting
less, it was making every suggestion cheap to check.
